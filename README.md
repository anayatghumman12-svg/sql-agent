# Autonomous SQL Analysis Agent

An API where a user asks a question in plain English about a database. A background agent writes the SQL, runs it, reviews its own result, retries if it is not confident (max 3 attempts), and returns a human-readable answer.

## Architecture

```
Client -> FastAPI (/ask) -> Celery task queued -> Redis (broker + job state + cache)
                                   |
                                   v
                    Agent loop (inside Celery worker)
                    1. Read question + schema
                    2. Generate SQL
                    3. Execute against Postgres
                    4. Agent reviews its own result: trustworthy or retry?
                    5. If retry: agent revises its approach (max 3 attempts)
                    6. Summarize result in plain English
                                   |
                                   v
        Redis stores: status, answer, SQL used, attempts, cache
Client -> FastAPI (/status/{job_id}) -> polls Redis -> returns result when done
```

Docker Compose services (exactly four): `api`, `worker`, `redis`, `postgres`.

Framework: LangChain. Model: configured in `app/settings.py`.

## Design rule: the agent judges, not Python

There is no `if row_count == 0: retry()` style logic. After each query, the result is passed back to the model, which reasons about whether the answer makes sense, whether the number is plausible, and whether edge cases (such as order status) were handled. The model returns a decision (accept / retry / give up). Python only routes on that decision.

## Dataset

Synthetic e-commerce data, generated by pure SQL in `db/02_seed.sql` (using `generate_series` and a fixed `setseed`, so the data is identical on every fresh start). It is created and loaded automatically by the postgres container on `docker compose up`, with no extra container or manual step.

I chose synthetic data because it lets me plant specific traps and control the messiness, so every expected answer can be verified independently.

### Tables

| Table | Columns | Notes |
|---|---|---|
| `customers` | customer_id (PK), name, email, city, signup_date | ~10% of `city` is NULL |
| `products` | product_id (PK), name, category, price | Categories overlap (e.g. "Electronics" vs "Gadgets") |
| `orders` | order_id (PK), customer_id (FK), order_date, status, discount_code | status: delivered, shipped, cancelled, refunded; discount_code mostly NULL |
| `order_items` | item_id (PK), order_id (FK), product_id (FK), quantity, unit_price | `unit_price` can differ from the product's current price |
| `payments` | payment_id (PK), order_id (FK), amount, method, paid_at | Some orders have more than one (partial) payment |

Size: 2,000 customers, 200 products, 20,000 orders, ~60,000 order items, ~21,000 payments.

### Messiness

- Around 10% of `customers.city` values are NULL.
- Overlapping categories: "Electronics" / "Gadgets", "Home" / "Home & Kitchen".
- `orders.discount_code` is mostly NULL.
- Some `order_items.unit_price` values differ from `products.price` (simulating price changes over time).

### Deliberate traps

| # | Trap | Naive query | Correct query | Difference |
|---|---|---|---|---|
| 1 | Cancelled / refunded orders | Sums every order | Excludes `cancelled` and `refunded` | +4,791,990.59 (~25.6% overstated) |
| 2 | Historical price | `products.price * quantity` | `order_items.unit_price * quantity` | +3,916,171.97 (~20.9% overstated) |
| 3 | Duplicate join | Joins `orders` to `payments`, double counting orders with 2+ payments | Aggregate payments per order first, or avoid the join | +3,743,270.27 (~20.0% overstated) |

Correct revenue (delivered + shipped orders, using order_items.unit_price, no payments join) = 18,748,156.00. Queries used to measure these differences are in `scripts/trap_checks.sql`.

## API

`POST /ask`

```json
{ "question": "..." }
```

Returns `{ "job_id": "abc123" }`.

`GET /status/{job_id}`

```json
{ "status": "pending" }
```

```json
{
  "status": "done",
  "answer": "...",
  "sql_used": "...",
  "attempts": 2,
  "cached": false
}
```

```json
{
  "status": "failed",
  "reason": "Agent could not produce a confident result after 3 attempts"
}
```

### Caching

Every question is normalized (lowercased, punctuation and extra whitespace removed) and checked against Redis before the agent runs. A repeated question returns instantly with `"cached": true`.
